# symptom-to-fix

这是一个专为 AI 编码助手（Agent）设计的技能规范（Skill），用于处理**原因不明、逻辑复杂的 Bug**。

它提供了一套标准化的 6 步闭环流程：**先锁定问题范围 -> 用失败复现定位根因 -> 产出方案与测试两份文档 -> 经用户确认后按测试驱动（先失败再通过）修复 -> 清理调试痕迹并复测交付**。

> **适用场景**：报错原因复杂、偶发故障、链路异常，或你要求「先定位排查、先别改代码」。  
> **不适用场景**：一眼能看出的笔误（Typo）、一两行代码的简单补丁、新功能开发。

---

## 核心流程（六个阶段）

```
1. 锁定问题范围 ──> 2. 抓取根因证据 ──> 3. 产出方案文档 ──> 4. 制定测试计划 ──> 5. 红绿测试修复 ──> 6. 清理与复测交付
  (查清4句事实)       (可复现/不改代码)   (2-3个方案等确认)    (8维度盘点用例)     (先失败再通过)     (全绿/产出Commit草稿)
```

1. **阶段 1：确定问题范围（说清要修什么）**  
   - 优先自行翻阅仓库代码、日志、配置和历史 Git 提交，不询问仓库里已有内容。
   - 记录当前工作区初始改动状态（`git status --short`），避免后续夹带无关修改。
   - 总结带有明确出处的四句事实：当前现象、期望与实际差距、修好的验收标准、本次明确不修的范围。
   - 仓库查不到、只能由用户提供的现场事实或产品决定，用一轮选择题集中确认。

2. **阶段 2：定位根本原因（只排查，不改代码）**  
   - 依赖 `diagnosing-bugs` 技能。
   - 写出一条当前必定执行失败的脱敏**最小复现命令**。
   - 提出假设并进行单变量打点探测（日志附带唯一前缀，如 `[DEBUG-abc1]`），用代码机制解释失败原因，排除竞争假设。
   - 本阶段不写正式业务代码，复现命令保持失败状态。

3. **阶段 3：编写问题与方案文档**  
   - 在仓库 `.scratch/bug-<短名>/problem-and-solutions.md` 下记录排查结果。
   - 提出 2–3 个可行方案（包含改动点、修复机制、影响面、回滚方案与风险），给出推荐方案和测试切入点（Seam）。
   - 默认由主 Agent 写方案；只有不同方向存在相互独立、读代码仍答不了的未知时，才为每个方向并行派一个 Subagent。
   - 主 Agent 先比较各方案的问题和代价，再尝试合成更优方案；没有更优方案就如实记录。
   - 复用当前任务已有的方案确认或代选授权；没有覆盖当前方案和测试 seam 的授权时，再向用户询问，未确认前禁止进入编码修复阶段。

4. **阶段 4：制定全面测试计划**  
   - 在 `.scratch/bug-<短名>/test-plan.md` 下从 8 个维度梳理测试用例（回归、根因分支、常规路径、边界空值、异常重试、状态并发、兼容性、周边防回退）。
   - 将所有验收目标和方案风险映射到「本轮必做」测试用例。
   - **响应停步指令**：若用户要求了「先别改代码 / 先排查」，在交出两份文档后即刻停止。凡在阶段 6 之前停下，都先清掉调试打点，复现命令保留。

5. **阶段 5：测试驱动修复（先失败，再通过）**  
   - 依赖 `tdd` 技能，且必须在方案确认后才能开始。
   - 每次只处理一条用例：先写测试并确认因预期原因失败（Red），再写刚好通过的实现代码（Green），把运行输出证据写回测试文档。

6. **阶段 6：清理、复验与交付**  
   - 删除所有临时调试打点，使用唯一前缀全局搜索确认生产代码零残留。
   - 重跑原始复现命令和所有必做测试用例，确保全绿。
   - 对照初始 Git 状态审查增量 Diff，输出 Commit 建议草稿留在对话与文档中；默认不提交 Git，用户明确授权提交、推送或合并时完成对应交付动作。

## 长任务续航（可选）

`SKILL.md` 本身不依赖 `/goal`。在支持 `/goal` 的 Cursor 环境里，可以这样启动长时间修复：

```text
/goal 使用 symptom-to-fix 修复 <问题>，直到原始复现和全部本轮必做测试通过、调试痕迹清理完成，并完成最终增量审查
```

不要只写「直到所有测试通过」：测试范围可能不完整，也可能包含与本次修复无关的历史失败。原始症状、必做用例、清理和改动审查都应写进目标。

## 安装方法

### 方式 1：使用 skills CLI 安装（待仓库公开后）

```bash
npx skills add Shengjingwa/symptom-to-fix
```

### 方式 2：手动复制到本机

将 `skills/symptom-to-fix/` 整个目录复制到对应工具的技能目录下：

- **Cursor**：`~/.cursor/skills/symptom-to-fix/`（Windows 路径为 `%USERPROFILE%\.cursor\skills\symptom-to-fix\`）
- **Claude Code**：`~/.claude/skills/symptom-to-fix/`
- **Codex**：`~/.codex/skills/symptom-to-fix/`

> **注意**：
> 1. 目录名必须严格保持为 `symptom-to-fix`（与 `SKILL.md` 内的 `name` 一致）。
> 2. 复制完成后，建议打开一次 `symptom-to-fix/SKILL.md` 确认文件可读。
> 3. 在对话中输入 `/symptom-to-fix`，或在提出「排查 / 原因看不出 / 先别改代码」时由 Agent 自动触发。
> 4. 若在 Cloud Agent 或远程容器中使用，请将目录放入仓库根目录下的 `.cursor/skills/symptom-to-fix/`。

## 前置依赖

本技能依赖以下两项基础工程技能（均来自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `skills/engineering/` 目录）：

- **`diagnosing-bugs`**：第 2 阶段用于复现与根因诊断。
- **`tdd`**：第 3、5 阶段用于确定测试切入点与执行红绿测试。

若环境中缺失对应技能，Agent 会标记依赖阶段为 `blocked`，提示缺失项及安装地址；其它不依赖该阶段的工作继续，缺失阶段不能报告为完成。

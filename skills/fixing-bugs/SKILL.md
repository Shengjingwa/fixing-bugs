# 修 bug

先走能用的最轻一档，碰到升级信号再升档。三档共用「开头」「升档」「依赖」「停下与交付」四节；快修、排查两档的步骤在本文件，完整档的步骤在同目录 [full.md](full.md)，升到完整档时才读。

## 开头

1. 运行 `git status --short`，记下已有改动和未跟踪文件。这是基线，本轮修复不碰它们。
2. 用一句话写清现象和怎样算修好，带出处（用户原话、日志、Issue 或仓库路径）。「修好」写成一条可观察的命令输出或界面状态。
3. 定起始档位：用户指定了档位就从那一档开始；没指定时，按下表选能用的最轻一档。

| 档位 | 起始条件 |
|---|---|
| 快修 | 日志或报错直接指向代码，读那段代码就能确认原因 |
| 排查 | 原因不明 |
| 完整 | 用户说「先别改」或要求留文档 |

仓库里查得到的（代码、日志、配置、以前的提交）自己查。只有用户知道的现场事实或产品决定，用宿主的问答工具一次问齐，等待期间继续做不依赖答案的部分。

**完成：** 对话里有基线摘要、一句话现象和修好标准、起始档位及理由。

## 升档

每一档的每一步都留意两类信号。

**诊断信号**（快修 → 排查），碰到任一条：
- 读代码确认不了原因，只能猜
- 修之前那条命令不失败，或失败的样子和报告的症状不一样
- 修完那条命令仍失败
- 日志指向不止一处，可能不止一个原因

**风险信号**（快修或排查 → 完整），确认根因后、改代码前检查，碰到任一条：
- 修法有两种以上，且实质不同
- 改动涉及对外接口、协议、数据格式、存量数据或迁移
- 改动跨多个模块
- 用户说「先别改」或要求留文档（任何时候出现都算）

碰到信号时：
- 档位是 agent 自己选的：直接升档，在对话里写一句碰到了哪条信号。
- 档位是用户指定的：停下，说明碰到了哪条信号，问用户要不要升。用户不升，就按原档做完，在报告里写明这条风险。

升档时，已有的事实、复现命令和打点证据全部沿用，只补新档位缺的部分。

## 快修

只走本节步骤；`diagnosing-bugs` 和 `tdd` 留给排查档和完整档。

1. 读报错指向的代码，写一句根因：哪段代码、在什么输入下、怎样产生了报告的症状。
2. 检查风险信号。
3. 找或写一条命令，让它在修之前因为这个 bug 失败。已有测试、新加测试或复现脚本都行；能放进现有测试套件的，写成测试。运行它，确认失败的样子和报告的症状一致。
4. 改代码，直到这条命令通过。
5. 跑相关测试：改动所在模块的测试，以及覆盖了被改代码调用方的测试。
6. 按「停下与交付」收尾。

这段代码没有能用命令驱动的入口时（例如纯界面样式），第 3 步改为：改完写出人工验证步骤，报告里写明「没有自动验证」和做不出命令的原因。

**完成：** 根因能指到具体代码行；修之前失败、修之后通过的命令和输出都在对话里，或已写明没有自动验证及原因；相关测试通过。

## 排查

1. 读 `diagnosing-bugs`，做完 `Build a feedback loop`、`Reproduce + minimise`、`Hypothesise`、`Instrument`。复现命令、偶发问题和无法复现时的停止条件都以那份 skill 为准。
2. 根因说清后，检查风险信号。
3. 按 `diagnosing-bugs` 的 `Fix + regression test` 修：按它的 correct seam 判据选位置，直接写回归测试，看它因为这个根因失败，再修到它通过。没有 correct seam 时，用原始复现命令代替回归测试，并在报告里写明原因。
4. 跑相关测试，重跑未缩小的原始复现命令。
5. 按「停下与交付」收尾。

**完成：** 有一条已运行、能稳定复现原症状的命令；根因有打点证据，主要竞争假设有排除证据；回归测试（或原始复现命令）修前失败、修后通过；未缩小的原始复现命令通过；相关测试通过。

## 完整

读同目录 [full.md](full.md)，从完成条件还没满足的那一段接着做。

## 依赖

排查档用 `diagnosing-bugs`；完整档用 `diagnosing-bugs` 和 `tdd`。进入用到它的步骤前，按宿主的 skill 清单和已知安装位置找到并读出它的 `SKILL.md`。读不到时，把这一步标为 `blocked`，写明缺哪个，以及上游地址 <https://github.com/mattpocock/skills/tree/main/skills/engineering>，然后继续做不依赖它的部分。`blocked` 的步骤不能报告为完成，也不能凭猜测补上。

## 停下与交付

各档加的诊断打点，每条都带本轮唯一前缀（例如 `[DEBUG-a4f2]`），收尾时按前缀清理。

在交付前停下时（等用户回答、`blocked`、用户说「先别改」），先清掉生产路径上的诊断打点，做法同下面第 1 步；复现命令和一次性 harness 保留。

交付：
1. 清掉诊断打点，删除一次性 harness，或移到明确标为 debug 的位置。用本轮唯一前缀做字面量搜索，直到生产路径没有命中。
2. 运行 `git status --short`、`git diff` 和 `git diff --cached`。未跟踪的新文件两条 diff 都看不到，逐个打开检查。对照开头的基线，只审本轮增量。
3. 在对话里报告：
   - 最终档位，以及碰到过哪些升级信号
   - 根因：哪段代码、在什么条件下、做了什么
   - 改动：改了哪些文件、怎么改的
   - 验证：修前失败和修后通过的命令及输出（脱敏），以及相关测试结果；没有自动验证时，写人工验证步骤
   - commit 信息草稿：根因、改法，以及排除掉的其他解释
4. 改动默认留在工作区。用户明确授权提交、推送或合并时，按授权完成对应动作并报告结果。

# 原因不明的 bug

按下面 6 段做。第 3、4 段分别留下方案文档和测试计划；正式测试与修复从第 5 段开始。用户说「先别改」时，做到第 4 段并交出两份文档后停。在第 6 段之前停下时，先清掉生产路径上的诊断打点（做法同第 6 段第 1 步）；原始复现命令和一次性 harness 保留。

第 2 段依赖 `diagnosing-bugs`，第 3、5 段依赖 `tdd`。进入对应阶段前，先按当前宿主的 skill 清单和已知安装位置解析并读取依赖的 `SKILL.md`；确认不可读后，将依赖阶段标为 `blocked`，说明缺哪个和上游地址，并继续不依赖该阶段的工作。缺失依赖的阶段不能报告为完成，也不能用猜测替代。

---

## 1. 说清要修什么

仓库里能查到的，自己查：代码、日志、配置和以前的提交。开始时运行 `git status --short`，记录已有改动和未跟踪文件，不混进本轮修复。

仓库和现有材料查完后，四句里仍缺少、且只能由用户提供的现场事实或产品决定，才提问；当前任务或对话已有答案直接复用。需要提问时，用宿主提供的问答工具一次集中收集当前问题，并在等待期间继续不依赖该答案的工作。

这一段结束时，对话里要有四句，每句带出处（用户原话、Issue、测试名或仓库路径）：
- 现在看见什么
- 期望是什么，实际是什么
- 怎样算修好（一条可观察的命令输出或界面状态）
- 这次明确不修什么

**完成：** 四句及出处都能指出；查证路径或命令、开始时的工作区改动摘要已记录；问过人时还能指出用户回复。

---

## 2. 找到原因

读并执行 `diagnosing-bugs`：
- 做完 `Build a feedback loop`、`Reproduce + minimise`、`Hypothesise`、`Instrument`
- 读 `Fix + regression test` 的 correct seam 判据：正式测试必须走真实调用链上的同一种 bug；过浅的测试会给假信心
- 正式回归测试、修复和清理留到本文件第 5、6 段

复现命令、偶发问题和无法复现时的停止条件都以那份 skill 为准。用测试搭建的反馈循环只作一次性 harness。本段停在根因说清、复现命令仍失败。

**完成：** 有一条已运行、能稳定捕获原症状的脱敏复现命令；复现已最小化；3–5 条可证伪假设已排序；成立的根因机制有探测证据，主要竞争假设有排除证据；每次探测只动一个变量，诊断打点带唯一前缀；该机制能解释失败。

---

## 3. 写问题与方案文档

先读 `tdd` 的 `Seams: where tests go`。原因清楚后提出 2–3 条各自能达到验收目标的完整方案；方案必须消除或隔离已证实的根因，只遮住症状的方向放进淘汰项。

路径：`.scratch/bug-<短名>/problem-and-solutions.md`。按顺序写：
1. **事实问题：** 第 1 段四句及出处
2. **证据与根因：** 原始复现命令、一次性 harness 路径、诊断前缀、脱敏失败输出、根因机制
3. **范围与约束：** 受影响范围、已有改动、兼容要求、风险、不修范围
4. **候选方案：** 每个方案的改动位置、修复机制、影响面、发布/回滚办法、风险和剩余未知
5. **比较与推荐：** 先写失败条件、问题和代价，再写收益、推荐理由及不选理由
6. **测试 seam：** 真实调用链上可稳定观察行为的 seam；没有 correct seam 时写证据，并指定原始复现命令作回归
7. **禁区：** 只实施选定方案；保持既有协议；保留见过失败的回归测试；不碰开始时已有的无关改动

默认由主 agent 用同一组事实写方案。只有各方向存在相互独立、读代码仍答不了的关键未知，且环境支持并行时，才为每个方向派一个 subagent。每个 subagent 只拿已证实的根因、验收目标、不修范围和自己的方向，不得重查根因；交回改动位置、修复机制、影响面、回滚办法和剩余未知，最多给两个实质不同的完整变体。

主 agent 收回结果后重新比较，并尝试合成一个解决现有候选问题的更优方案；合成不出来就写「未发现更优合成方案」。只有一条可行方案时不凑数，记录其他方向的淘汰证据。

先检查当前任务或对话中是否已有覆盖推荐方案和测试 seam 的明确确认，或是否已授权 agent 在该范围内选择；有则记录授权来源并继续，不重复询问。否则把推荐方案和测试 seam 放在同一次提问中；未确认时标 `待确认`，第 4 段可以继续，第 5 段不能开始。

**完成：** 文档在；事实、根因和方案都有证据；有 2–3 个完整方案，或有唯一方案的淘汰证据；每个方案覆盖验收目标并列出问题、影响与风险；推荐理由、seam 和确认状态明确。

---

## 4. 写测试计划

路径：同一目录下的 `test-plan.md`。写正式测试和修复前先把用例盘点完整。每条用例写：编号和名称；覆盖目标或风险；`本轮必做` / `扩展`；层级和 seam；前置数据；输入与操作；可观察结果；执行命令或人工步骤；`planned` / `red` / `green` / `blocked` 状态及本轮证据。

逐项盘点，适用的写用例，不适用的写 `N/A` 和理由：
1. 原症状的正式回归
2. 根因最小分支和推荐方案改变的机制
3. 正常路径和验收目标
4. 边界、空值、临近输入和易混淆变体
5. 错误、超时、取消、重试和失败恢复
6. 状态迁移、顺序、幂等和并发
7. 配置、数据、协议、平台和版本兼容
8. 相邻功能不回退，不修范围保持原状

每条验收目标、每个复现条件、推荐方案的每个可测试风险，至少映射一条 `本轮必做` 用例。发布、回滚等不能靠测试证明的风险单列验证或缓解办法，不编成测试；仓库全量测试只能补充这张映射，不能代替它。无法执行的用例标 `blocked` 并写清缺什么证据；本轮必做只要有一条 `blocked`，验收就不能通过。

**完成：** 文档在；八个维度都有用例或 `N/A` 理由；验收目标、复现条件和可测试风险都有本轮必做用例，其他风险有验证或缓解办法；第一条正式回归落在推荐 seam，或已证明没有 correct seam 并改用原始复现命令；此时尚未写正式测试或修复。

---

## 5. 先失败再通过

继续执行 `tdd`。先检查方案和 seam 已由用户确认，或用户已授权 agent 选择；这项授权同时满足本轮 `tdd` 的预先约定 seam 要求，不重复询问。若授权不存在则停在编码前；确认内容有变化时，先回第 3、4 段更新两份文档。

一次只做一条。先把最小复现收成推荐 seam 上的第一条正式回归测试，运行并确认它因预期根因失败，标 `red`；再写刚好让它通过的实现，贴输出并标 `green`。没有 correct seam 时，用文档指定的原始复现命令完成同样的 red-green。

再按测试计划逐条做。验证既有行为的用例可以直接 `green`；证明行为改变的用例必须先 `red` 再 `green`。每次运行后立即更新状态和证据。方案走不通时停下，回第 3、4 段更新后重新开始。

**完成：** 第一条正式回归有预期失败和随后通过的输出；原始复现命令已通过；全部本轮必做用例都是 `green` 并有本轮证据。没有 correct seam 时，原始复现命令同时有修复前失败和修复后通过的输出。

---

## 6. 验收

先清理，再针对最终代码跑证据：
1. 清掉诊断打点；删除一次性 harness，或移到明确标为 debug 的位置。用本轮唯一前缀做字面量搜索，直到生产路径无命中
2. 重跑未缩小的原始复现命令，记录输出
3. 重跑全部本轮必做用例，把最终状态和输出写回测试计划
4. 把根因、否决方案和禁区整理成 commit 信息草稿，写在对话里并追加到方案文档
5. 跑 `git status --short`、`git diff` 和 `git diff --cached`；两条 diff 都看不到新增但未跟踪的文件，逐个打开检查。对照开始时的基线只审本轮增量，确认都符合选定方案和禁区。默认保留改动在工作区；如果用户已明确授权提交、推送或合并，按授权完成对应交付动作并报告结果。

**完成：** 清理后的最终实现通过原始复现和全部本轮必做用例；生产路径没有诊断前缀；本轮每个增量都符合选定方案，开始时的无关改动未被触碰；两份文档已更新；对话里有证据摘要和 commit 信息草稿；按用户要求的交付动作已完成，或明确报告仍待执行的外部动作。
